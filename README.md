# Ellow Launchpad

Development foundation for Ellow Launchpad — a candidate career-launch platform (in future phases).

- **Phase 1**: monorepo structure, a Next.js frontend, a FastAPI backend, PostgreSQL, Docker Compose, and the development workflow.
- **Phase 2**: authentication and an RBAC foundation — registration, login, access/refresh tokens, a current-user endpoint, and a minimal role-based authorization mechanism.
- **Phase 3**: candidate identity — profile, education, skills, work experience, career preferences, a deterministic profile-completion score, and a guided onboarding flow.
- **Phase 4**: the real candidate dashboard at `/app` — profile completion, readiness breakdown, a deterministic next-action, honest "coming soon" placeholders for unbuilt modules.
- **Phase 5** (this state): the Resume Centre — upload, versioning, and a manual (non-AI) review workflow. See [Resume Centre](#resume-centre) below. No other business features (interviews, credits, jobs, etc.) are implemented yet.

## Architecture

```
Browser → Next.js (apps/web) → FastAPI (apps/api) → PostgreSQL
```

The browser only ever talks to Next.js. Next.js's own Route Handlers and Proxy (`proxy.ts`) call FastAPI server-side over the Docker network (`http://api:8000`); the browser never sees that hostname and never holds a raw access/refresh token (see [Authentication architecture](#authentication-architecture) below).

See [.env.example](.env.example) for the full list with defaults:

- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` — PostgreSQL configuration
- `DATABASE_URL` — SQLAlchemy async connection string used by the API and Alembic
- `API_PORT` — host port the API is published on
- `WEB_PORT` — host port the web app is published on
- `NEXT_PUBLIC_API_URL` — API base URL used by the browser
- `API_INTERNAL_URL` — API base URL used by the Next.js server itself (the `api` Docker service name, not `localhost`)
- `JWT_SECRET_KEY` — signs access tokens. The committed default is dev-only and clearly marked as such; **generate a real one for any shared/deployed environment** (`python3 -c "import secrets; print(secrets.token_urlsafe(64))"`)
- `JWT_ALGORITHM` — JWT signing algorithm (default `HS256`)
- `ACCESS_TOKEN_EXPIRE_MINUTES` — access token lifetime (default 15)
- `REFRESH_TOKEN_EXPIRE_DAYS` — refresh token lifetime (default 30)
- `RESUME_STORAGE_DIR` — local-disk directory resumes are stored under inside the `api` container (default `/app/storage/resumes`, backed by the `resume_storage` named volume)
- `RESUME_MAX_SIZE_MB` — maximum accepted resume upload size (default 5)

PostgreSQL's port is intentionally not published to the host — only `web` and `api` are reachable outside the Docker network.

## Authentication architecture

### Roles

Six fixed roles exist from the start: `CANDIDATE`, `INTERVIEWER`, `CAREER_COACH`, `RECRUITER`, `ADMIN`, `SUPER_ADMIN`. They're seeded idempotently on every API startup (`app/services/roles.py`, `ON CONFLICT DO NOTHING`) — no business logic is tied to any role yet beyond the `/api/v1/rbac-demo/admin-only` example endpoint, which exists purely to prove `require_role()` works end to end. New users are assigned `CANDIDATE` on registration; there is no self-service way to acquire another role, and no hardcoded super-admin account — promoting a user is a direct database operation for now (`INSERT INTO user_roles ...`), documented here rather than automated, since a scripted bootstrap-admin command would just move the "secret default password" problem rather than remove it.

### Tokens

- **Access token**: a short-lived (15 min default) JWT, payload limited to `sub` (user id), `type`, `iat`, `exp` — no roles or email baked in. Every request re-reads the user's roles from the database (`app/api/deps.py::get_current_user`), so a role change or deactivation takes effect on the very next request instead of waiting for the token to expire.
- **Refresh token**: an opaque, high-entropy random string (not a JWT), persisted server-side as a SHA-256 hash (`refresh_tokens` table). Only the hash is stored, so a database read alone never yields a usable credential. Every refresh **rotates** the token: the old one is marked revoked and linked to its replacement (`replaced_by_id`), and a revoked token presented again is treated as theft — the entire chain for that user is revoked (`app/services/auth.py::rotate_refresh_token`). Logout revokes the current token directly.
- **Known limitation**: access tokens can't be revoked before they expire (they're stateless). Compromise during that ≤15-minute window is bounded by the short lifetime, not by immediate revocation. This is a deliberate v1 tradeoff, not an oversight.

### Browser ↔ Next.js ↔ FastAPI

FastAPI's `/api/v1/auth/*` endpoints are a plain token-issuing JSON API — they know nothing about cookies or browsers. Next.js is the only thing that does:

- `app/api/auth/{register,login,refresh,logout}/route.ts` call FastAPI server-side and set/clear **httpOnly** cookies (`launchpad_access_token`, `launchpad_refresh_token`) on the browser response. The raw tokens never reach client-side JS (`lib/auth/session.ts`, `lib/auth/cookies.ts`).
- `proxy.ts` (Next's Proxy/Middleware convention — Next 16 renamed `middleware.ts`) guards `/app/:path*`: if there's no access-token cookie but there is a refresh-token cookie, it silently refreshes and sets fresh cookies on the response *before* the page renders. Server Components can't write cookies themselves, which is why this lives in the proxy rather than on the page.
- The `/app` page itself is a Server Component that calls FastAPI's `/me` directly (`lib/auth/session.ts::getCurrentUser`) and redirects to `/login` if that fails — it is the actual authorization check, not just a UX nicety.

Cookie flags: `httpOnly`, `SameSite=Lax`, `Secure` in production only (so plain `http://localhost` still works in dev), `path=/`. `SameSite=Lax` is the CSRF defense: neither cookie is sent on a cross-site POST, so a forged request to `/api/auth/logout` or `/api/auth/refresh` from another origin arrives with no session cookie attached. The refresh cookie uses `path=/` rather than a narrower `/api/auth` scope specifically because the proxy needs to read it on `/app` requests too.

**Frontend route protection is not a security boundary.** The proxy and the `/app` page's redirect are UX — every protected FastAPI endpoint enforces its own authorization independently via `Depends(get_current_user)` / `Depends(require_role(...))`, and will reject an unauthenticated or under-privileged request regardless of what the frontend does.

## Resume Centre

### Scope and non-goals

Launchpad owns resume submission, versioning, review requests, review status, and presenting feedback to the candidate. It deliberately does **not** own AI parsing/scoring — that belongs to a separate Profile Analyzer product that doesn't exist in this codebase yet. The candidate-facing workflow (`UPLOADED → UNDER_REVIEW → COMPLETED`) is provider-agnostic by design: `ReviewResult.reviewer_type` supports `HUMAN`/`AI`/`HYBRID`, but Phase 5 only ever writes `HUMAN` results, and only ever manually (there is no reviewer portal yet — see below).

### Storage

`app/services/resume_storage.py` defines a small `ResumeStorage` protocol (`save`/`open`/`delete`) with one implementation, `LocalFileStorage`, backed by the `resume_storage` Docker volume. Swapping in S3/object storage later means implementing that same protocol again, not touching any resume business logic. Storage keys are always server-generated (`{candidate_profile_id}/{uuid4().hex}{extension}`) — the original filename is stored only for display and is never used as a path, so there's no path-traversal surface.

### Versioning and review-request concurrency

Every upload creates a new version; none are overwritten. The candidate's `CandidateProfile` row is locked (`SELECT ... FOR UPDATE`) for the duration of version-number computation, so two concurrent uploads for the same candidate can't both compute "next version = 2" — backed by a `UNIQUE(candidate_profile_id, version)` constraint as a last-resort safety net. Similarly, at most one non-`COMPLETED` review request can exist per resume, enforced by a Postgres **partial unique index** (`uq_review_requests_active_per_resume ... WHERE status != 'COMPLETED'`), not just an application-level check.

### No reviewer portal yet

`app/services/resume_review.py::start_review` / `complete_review` exist and are tested, but **no API endpoint exposes them** — there is no admin/recruiter/reviewer UI in this phase (out of scope per the brief). A completed review is currently written by calling `complete_review` directly (see the manual-verification steps used during development), which is the intended Phase-5-appropriate way to simulate what a future reviewer tool will do through its own API, without inventing that tool now.

## Notes

- `packages/` and `infra/` are placeholders for later phases.
- Promoting a user to a role beyond `CANDIDATE` is currently a manual database operation; there is no admin UI or bootstrap script yet (see [Authentication architecture](#authentication-architecture)).
- Resume files on disk are not deleted when their database rows are (there is no delete-resume feature in this phase to trigger it) — acceptable for now, worth revisiting if a delete feature is added later.
